### 3. Concepts to be clarified

This section of remarks has 2 purposes:
1. Define some common languages and concepts for future use, so that we can stop wasting time explaining our "actual meanings".
2. Sketch out some important concepts (to me) that may also be helpful for future design. 

#### Physical vs Logical

Let's use the word "logical" to refer to the semantic meaning of the query or operator. 
For examples, if two operators map every input to the same output, then they are logically the same, and should correspond to a single logical operator.

On the other hand, "physical" should refer to the actual implementation of the operator, which may have different performance characteristics. 
For example, a single `Join` operator in logical level may correspond to multiple physical implementations, 
like `HashJoin`, `MergeJoin`, etc.

#### Inter-lifecycle-stage vs Intra-lifecycle-stage distribution

"Inter-lifecycle-stage distribution" means that we can distribute the DAG execution into different stages of the data life cycle.
While "intra-lifecycle-stage distribution" means that we can distribute the execution into multiple `Executor`s within a single stage of the data life cycle.

Both disbributions should eventually be considered by the controller, but for v1 we do not need either of them,
which means, we only consider single `Executor` and single lifecycle stage.

#### Inter-`Executor` vs Intra-`Executor` parallelism

We can benefit from parallelism by distributing the DAG execution into multiple `Executor`s. 
However, there's another level of parallelism: the "intra-`Executor` parallelism", which means that even within a single `Executor`, we can still have multiple threads or processes to execute the DAG in parallel.

For example, we may have multiple machines using DataFusion to execute part of the task, and within each machine, DataFusion itself can leverage its internal parallelism to further speed up the execution.

Thoughts for the future:
1. DB engines like DataFusion and DuckDB all have their own internal parallelism, which is the "intra-`Executor` parallelism". However, none of them support the "inter-`Executor` parallelism". I feel this can be more interesting.
2. We can have the controller to take over the inter-`Executor` optimization, and leave the intra-`Executor` optimization to controller user applications.
3. To make controller be able to optimize the inter-`Executor` parallelism, we need to think carefully about how to model the `Executor`.

#### Symbolic plan vs Concrete plan

In my understanding, a symbolic plan is a plan which is:
1. Conceptually clear and sound, 
2. but not executable by any downstream platform without further processing.

I think `ASAPController` should output a symbolic plan, which can be further translated into a concrete plan by downstream platforms.
Or the translation can also be intergrated in `ASAPController`, but it should be modularized and separate from the symbolic plan generation.

A concrete plan is a downstream-platform-executable plan, which is generated from the symbolic plan.
Ideally each symbolic plan output by `ASAPController` should unambiguously correspond to a unique concrete plan.

#### !!! Important remark: The 4 pairs of concepts above are all orthogonal to each other!

For example, `ASAPController` may output a symbolic plan like the following:
1. Each data collector locally compute a CMS and send that CMS into the backend.
2. The backend merges the CMSs from different data collectors. 
3. Multiple machines at the backends query the merged CMS in parallel to answer the group-by COUNT query.

The logical operator here can be `ApproximateAggregate` and the physical operator is `CMSAggregate`.
The plan defiens inter-lifecycle-stage distribution by having the first step executed at the data collector stage and the second and third step executed at the backend stage.
The plan also defines inter-`Executor` parallelism by having the third step executed by multiple machines, and each machine can further leverage intra-`Executor` parallelism to speed up the execution.

### 4. Peilin's ideal workflow towards an executable concrete plan via `ASAPController`

1. `ASAPController` outputs a symbolic plan
2. Downstream platforms translate the symbolic plan into a concrete plan.
3. Downstream platform further optimize the concrete plan by leveraging their internal optimization techniques.
4. Downstream platform execute the concrete plan.

Step 3 may look redundant, maybe it does not exist in `ASAPQuery` and `ASAPDataCollector`, but it is very likely to exist in ASAPFusion, because physical aggregate in DataFusion can be executed in parallel, and if that optimization is made depends on aggregation parameters and machine specifications. The latter one is likely to be something that `ASAPController` does not know about.
